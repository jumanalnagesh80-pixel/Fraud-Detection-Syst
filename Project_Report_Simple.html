1. Project Overview — what is this?

Sentinel is a complete software system that detects fraudulent financial transactions as they happen — in real time. Banks and payment companies lose billions every year to credit-card fraud, account takeovers, and suspicious wire transfers. This project is a working prototype of the kind of system those companies use to spot bad transactions and block them before money leaves the account.

It combines three big ideas into one product:

  • Machine learning — a model that has learned what fraud looks like from past examples.
  • Rule engine — hand-written rules ("if amount > $2,000 from a high-risk country at 3 AM…") for cases the model might miss or that we want to enforce explicitly.
  • A web dashboard — so a human analyst or admin can watch transactions arrive in real time, review alerts, and approve or block them.
In one sentence: Sentinel takes incoming transactions, scores them with both an ML model and a rule engine, and decides whether to approve, send for review, or decline — showing the result in a live web dashboard.

5. What is Machine Learning? (in plain English)

Imagine you want to teach a child to spot a fake $20 note. You don't write a list of rules — instead, you show them thousands of real notes and a few fake ones, and say "this is real, this is fake, this is real…". After enough examples, the child starts noticing patterns: the texture, the watermark, the ink color. They can now look at a brand-new note and guess "this looks fake."

That is exactly how Machine Learning works. We give a computer many examples of past transactions — each one labelled "fraud" or "not fraud" — and a mathematical algorithm finds the patterns. After training, the computer can score brand-new transactions and predict the chance they are fraudulent.

5.1 The three steps of ML

Step 1 — Training

Feed the algorithm thousands of past transactions. It adjusts millions of internal numbers until its predictions match the known labels as closely as possible.

Step 2 — Evaluation

We test the trained model on transactions it has never seen before, to measure how accurate it is (precision, recall, ROC-AUC).

Step 3 — Prediction

Once happy, we use the model in the live system. Every new transaction is fed in and the model outputs a fraud probability between 0 and 1.

Plus — Persistence

We save the trained model to a file (fraud_model.pkl) so the server can load it instantly on restart instead of retraining.

6. The ML model used in this project

This project does not use just one algorithm — it uses an ensemble (a team of three algorithms voting together). This is called a Voting Classifier with soft voting: each algorithm gives a probability, and the final score is the weighted average.

6.1 The three algorithms in the team

AlgorithmWhat it doesStrengthWeight
Random Forest Builds 120 different decision trees and averages their votes. Robust, handles missing data, hard to fool. 2
Gradient Boosting Builds 100 trees one at a time, each one fixing mistakes of the previous. Very high accuracy on structured data. 2
Logistic Regression A simple, fast linear model. Great baseline, very interpretable, fast. 1

The final score = 0.4 × RandomForest + 0.4 × GradientBoosting + 0.2 × LogisticRegression.

6.2 The features (inputs) the model looks at

For every transaction, the system extracts these numerical features and feeds them to the model:

  • Amount — how much money is being spent.
  • Country — encoded as a number; some countries flagged high risk.
  • Merchant category — e.g. groceries, gambling, crypto.
  • Device type — mobile, desktop, POS terminal.
  • Hour of day — 0 to 23. Fraud often peaks at unusual hours.
  • Card present? — was the physical card swiped, or was it online?

6.3 Risk levels and decisions

The combined score is between 0 and 1. The model converts it to a label and a decision:

ScoreRisk levelDecision
0.00 — 0.40lowapprove
0.40 — 0.65mediumapprove
0.65 — 0.85highreview
0.85 — 1.00criticaldecline

7. The Rule Engine

The ML model is powerful but it's a "black box" — it can be hard to explain exactly why a transaction was flagged. To fix that, we run a parallel rule engine with hand-written rules that are 100% explainable.

The rule engine produces a second risk score (0–1) and a list of human-readable reasons. The final score combines both:

final_score = 0.65 × ML_score + 0.35 × rule_score

7.1 The rules currently implemented

Rule nameTriggers when…Weight
high_amountAmount ≥ $2,000+0.30
high_risk_countryCountry is NG, RU, or CN+0.25
high_risk_merchantCategory is gambling, crypto, or wire_transfer+0.20
odd_hourTime is between midnight and 5 AM AND amount > $300+0.15
card_not_present_high_valueOnline transaction (no physical card) AND amount > $1,000+0.15
Each triggered rule is shown to the analyst with a clear sentence like "Amount $3,500 exceeds $2,000 threshold", making the system auditable.

8. Database — all 6 tables explained

Everything the system remembers is stored in a single SQLite file: fraud_detection.db. Inside that file there are 6 tables. Each Python class in src/database/models.py becomes one table.

8.1 Table: roles

The three permission groups in the system: admin, analyst, viewer. Each role stores a JSON map of permissions (e.g. {"manage_users": true}).

8.2 Table: users

Every login account. Stores the username, email, hashed password, profile fields (full name, country, currency), security info (failed login count, lockout time, optional 2-factor settings) and an optional "face descriptor" — a list of 128 numbers that uniquely identify the user's face for face login.

Important: Passwords are never stored as plain text. They are hashed using scrypt via Werkzeug.

8.3 Table: audit_logs

A timeline of every important action: logins, password changes, admin actions, transaction reviews. Records who did what, from which IP address, and when. This is what auditors and security teams need.

8.4 Table: transaction_records

Every transaction the system has scored. Stores the raw transaction (amount, country, merchant, hour, device), the model's prediction (fraud_probability, risk_level, decision), which rules triggered, and how long the scoring took (latency_ms). Optionally links to the user, account, and card.

8.5 Table: bank_accounts

Real-style bank accounts. Each row has an account number, IBAN, routing number, balance, available balance (balance minus pending holds), currency, country, and status (active, frozen, closed). One user can have many accounts.

8.6 Table: cards

Debit and credit cards tied to bank accounts. Importantly, the full card number (the PAN) is never stored — only:

  • A masked form like **** **** **** 4242
  • The last 4 digits (for display)
  • A SHA-256 hash of the full PAN (for matching)
  • A bcrypt hash of the CVV

This mirrors real-world PCI-DSS rules. Each card also tracks a daily limit, amount spent today, and toggles for international/contactless/online use.

9. How a transaction flows through the system

This is what happens, step by step, when a single transaction arrives:

  1. The transaction (e.g. "$520, US, online, 14:00, mobile") arrives at the POST /api/transactions endpoint.
  2. The backend checks the user is logged in (Flask-Login session).
  3. The transaction is sent to the FraudModel:
    • Features are extracted by the FeatureEngineer.
    • The ensemble of 3 algorithms produces a probability (e.g. 0.42).
    • The RuleEngine runs in parallel and produces its own score (e.g. 0.30).
    • The final score is computed: 0.65 × 0.42 + 0.35 × 0.30 = 0.378 → "low" → "approve".
  4. A TransactionRecord row is saved to the database.
  5. If the risk is "high" or "critical", the AlertManager creates an alert and pushes a Server-Sent Event so the dashboard updates immediately.
  6. An entry is written to audit_logs.
  7. The browser polls /api/transactions every 3 seconds and shows the new row in the live feed.

11. How to run and use the project

11.1 First-time setup

pip install -r requirements.txt

11.2 Generate synthetic training data (optional)

python main.py --mode generate --samples 10000

11.3 Train the model and save it (optional — happens automatically on first run)

python main.py --mode train --data data/synthetic/synthetic_transactions.csv

11.4 Start the web app

python main.py

# default login:  admin / admin123

13. Conclusion & future work

Sentinel demonstrates an end-to-end, production-style fraud detection platform built with widely used open-source tools. It shows how three disciplines come together to solve a real-world business problem:

  1. Software engineering — Flask web app, REST APIs, web UI, role-based authentication, and audit logging.
  2. Data engineering — synthetic data generation, feature engineering, and a normalized relational database.
  3. Machine learning — an ensemble classifier combined with an explainable rule engine, evaluated with industry-standard metrics.

13.1 What could be added next

  • Deep learning model (LSTM / Transformer) to capture user behaviour over time.
  • Graph neural networks to detect fraud rings — accounts that connect to each other suspiciously.
  • Real Kafka stream instead of polling for true high-throughput pipelines.
  • SHAP explanations on every ML decision for full interpretability.
  • Mobile app for end users to confirm/decline suspicious transactions on their phone.
