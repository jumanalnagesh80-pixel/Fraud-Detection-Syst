1. Executive Summary

Sentinel is an end-to-end real-time fraud detection platform built with Python, Flask, scikit-learn and a modern web frontend. It ingests transactions, scores them with a hybrid Machine Learning ensemble + explainable rule engine, decides whether to approve / review / decline them, and surfaces the decision in a live web dashboard for analysts and admins.

The system delivers four key things:

  1. Real-time scoring — every transaction scored in <50 ms with risk level and explanation.
  2. Hybrid intelligence — the ML model catches subtle fraud patterns; the rule engine provides auditor-friendly reasons.
  3. Operational dashboard — analysts watch a live feed, charts, alerts, and review queue.
  4. Compliance & audit — every login, decision and admin change recorded in an immutable audit log.

2. Project Overview

2.1 What is the project?

Sentinel simulates the kind of fraud-detection system that Visa, Mastercard, PayPal, Stripe and major banks operate. It is a working software product that:

  • Accepts financial transactions through a REST API.
  • Runs each one through an ML model trained on historical fraud data.
  • Runs each one through a rule engine of hand-written fraud heuristics.
  • Combines the two scores, makes a decision, and stores everything.
  • Streams the result to a browser dashboard live (Server-Sent Events).
  • Lets human analysts review, approve, or escalate flagged transactions.

3. Problem Statement & Objectives

3.1 The business problem

Global card fraud losses exceeded USD 33 billion in 2024. Pure rule-based engines cannot keep up with new attack patterns; pure black-box ML models fail audit/regulatory review. A hybrid system is needed.

3.2 Project objectives

  1. Score any transaction in under 50 ms.
  2. Achieve ≥ 0.95 ROC-AUC on synthetic fraud data.
  3. Provide a human-readable reason for every flagged transaction.
  4. Maintain a tamper-evident audit log for compliance.
  5. Serve 50+ concurrent dashboard users on commodity hardware.
  6. Be deployable as a single Docker container.

9. Machine Learning — Detailed

9.1 What is Machine Learning?

Imagine teaching a child to spot a fake banknote. You don't write rules — instead you show thousands of real and fake notes labelled "real / fake". The child notices patterns: paper feel, watermark, color. Then on a brand-new note, they can guess.

Machine Learning works the same way. We feed the algorithm thousands of labelled past transactions. The algorithm internally adjusts millions of numbers until its guesses match the labels. Once trained, it can score brand-new transactions.

Mathematically: we are learning a function f(x) ≈ y, where x is the transaction features and y is fraud (0 or 1). The "learning" part is finding the parameters of f that minimise prediction error on the training set.

9.2 Supervised classification

Sentinel uses supervised binary classification:

  • Supervised = we have labelled examples to learn from.
  • Binary = there are only 2 possible outcomes (fraud vs not-fraud).
  • Classification = we predict a category, not a number.

9.3 The Voting Ensemble

Instead of a single algorithm, Sentinel uses a VotingClassifier that combines three different ones. Each gives a probability; the final probability is a weighted average.

final_probability = 0.40 × RandomForest.predict_proba(x)[1]
                  + 0.40 × GradientBoosting.predict_proba(x)[1]
                  + 0.20 × LogisticRegression.predict_proba(x)[1]

9.3.1 Random Forest

  • Builds 120 decision trees on random subsamples of the data.
  • Each tree splits on features like "amount > $500?", "is_card_present?".
  • The forest's prediction is the majority vote.
  • Strengths: robust to outliers, tolerates missing values, hard to overfit.

9.3.2 Gradient Boosting

  • Builds 100 trees one after another; each new tree fixes the mistakes of the previous.
  • Uses gradient descent to minimise the log-loss.
  • Strengths: typically the most accurate algorithm on tabular data.

9.3.3 Logistic Regression

  • A linear model: p = sigmoid(w₁x₁ + w₂x₂ + ... + b).
  • Fast, low-memory, interpretable (each weight tells you how a feature affects fraud probability).
  • Acts as a sanity-check — if the simple model and the trees agree, confidence is high.

9.4 Feature Engineering

Before the model can use a transaction, the raw data must be transformed into a numeric vector. This is done by FeatureEngineer in src/data_processing/feature_engineer.py.

Raw fieldTransformationWhy
amount (float)StandardScaler (mean 0, std 1)Prevents large values from dominating distance-based math.
country (string)Label-encode + one-hot for top 20ML expects numbers; one-hot avoids fake ordering.
merchant_category (string)One-hot encodeSame reason.
device_type (string)One-hot encodeSame reason.
hour (int 0-23)Cyclic encoding: sin(2πh/24), cos(2πh/24)Hour 23 is close to hour 0; cyclic encoding captures that.
is_card_present (bool)Cast to 0/1Trivial.

9.5 Training Pipeline

  1. Generate / load data → 10,000 rows with 5% fraud rate (configurable).
  2. Train / test split → 80% train, 20% test, stratified on label.
  3. Fit the FeatureEngineer on train set only.
  4. Train each algorithm in the VotingClassifier.
  5. Evaluate on the held-out test set with 5 metrics.
  6. Save model with pickle to models/trained/fraud_model.pkl.

10. The Rule Engine

An ML model is statistically powerful but a "black box" — it cannot easily explain why a transaction was flagged. Auditors and customers demand reasons. The RuleEngine in src/models/rule_engine.py evaluates 5 hand-written, fully transparent rules in parallel.

10.1 The 5 rules

RuleConditionWeightReason text shown to user
high_amountamount ≥ $2,000+0.30"Amount $X exceeds $2,000 threshold"
high_risk_countrycountry ∈ {NG, RU, CN}+0.25"Country X flagged as high-risk"
high_risk_merchantcategory ∈ {gambling, crypto, wire_transfer}+0.20"Merchant category X is high-risk"
odd_hourhour < 5 AND amount > $300+0.15"Transaction at unusual hour H with $X"
card_not_present_high_valuenot is_card_present AND amount > $1,000+0.15"Online transaction with high amount $X"

10.2 Combining ML and rules

final_score = 0.65 × ml_probability + 0.35 × rule_score
final_score = clip(final_score, 0.0, 1.0)

10.3 Risk levels and decisions

final_scorerisk_leveldecisionWhat happens
[0.00, 0.40)lowapproveTransaction goes through silently.
[0.40, 0.65)mediumapproveGoes through, logged for trend analysis.
[0.65, 0.85)highreviewHeld; analyst gets a notification.
[0.85, 1.00]criticaldeclineBlocked; user notified; alert raised.

12. Authentication, Authorization & Security

12.1 Authentication (who are you?)

  • Username + password — primary; passwords hashed with Werkzeug's scrypt.
  • 2-Factor (optional) — TOTP code (Google Authenticator).
  • Face login (optional) — face-api.js extracts a 128-dim descriptor; on login, the captured descriptor is compared with cosine similarity ≥ 0.6.
  • Security question — fallback recovery, answer hashed.
  • Lockout — 5 failed attempts → 15-minute account lock.

12.2 Authorization (what can you do?)

Role-Based Access Control (RBAC). Three roles seeded at first run:

RolePermissions (excerpt)
adminmanage_users, manage_roles, retrain_models, view_audit_logs, export_data, manage_settings
analystview_dashboard, review_transactions, retrain_models, export_data
viewerview_dashboard, view_transactions (read-only)

12.3 Other security controls

  • Audit log on every login, password change, role change, transaction review.
  • CSRF protection on form posts via Flask-WTF.
  • SQL injection impossible — all queries via SQLAlchemy parameterised statements.
  • XSS mitigated — Jinja templates auto-escape variables.
  • PCI-DSS-style PAN handling — full card number never stored, only mask + sha-256 hash + last 4.
  • Email masking — non-admins see a***n@example.com.

21. Future Scope & Real-World Use Cases

  • Banks — every credit/debit-card swipe is scored in real time before authorization.
  • Payment gateways (Stripe, PayPal, Razorpay) — score every API call to block stolen cards.
  • E-commerce checkouts — Shopify, Amazon, Flipkart use similar systems to block bot purchases.
  • Telco SIM-swap detection — same patterns: unusual location + high amount + odd hour.
  • Crypto exchanges — flag wash trading and money laundering.
  • Insurance claims — same model architecture, different features.

22. Project Q&A — viva / interview style

Q1. In one sentence — what does Sentinel do?
Sentinel scores every financial transaction in real time using both a machine-learning ensemble and a rule engine, decides whether to approve / review / decline it, and surfaces the decision in a live dashboard.
Q2. Why a hybrid (ML + rules) instead of pure ML?
ML catches subtle patterns humans haven't thought of, but it is a black box. Rules are fully explainable and demanded by auditors. Combining both gives high accuracy and human-readable reasons.
Q3. Why three algorithms in the ML model?
Random Forest is robust, Gradient Boosting is highly accurate, Logistic Regression is interpretable. The ensemble's weighted average is more accurate than any single one (bias-variance trade-off).
Q4. How does the model "learn"?
During fit(), each algorithm adjusts its internal parameters to minimise prediction error on labelled training data. Trees split on the most informative features; logistic regression adjusts weights via gradient descent.
Q5. What features does the model use?
amount, country (encoded), merchant_category, device_type, hour-of-day (cyclic), is_card_present. Country and merchant become one-hot vectors; hour becomes sin/cos pair; amount is standard-scaled.
Q6. How is the data stored?
In a single SQLite file fraud_detection.db with 6 tables: roles, users, audit_logs, transaction_records, bank_accounts, cards. SQLAlchemy maps Python classes to these tables.
Q7. Why SQLite and not PostgreSQL?
SQLite needs zero configuration — perfect for development and demos. The code reads DATABASE_URL at startup, so switching to PostgreSQL is a 1-line change.
Q8. How does real-time work without WebSockets?
We use Server-Sent Events (SSE) — a simple HTTP streaming protocol. The browser keeps an open connection; the server pushes new transaction events on it. Lighter than WebSockets and built into HTML5.
Q9. How do you handle a million transactions a day?
Switch SQLite → PostgreSQL, add an index on processed_at, run Gunicorn with multiple workers, and put a Kafka stream in front. The ML model itself can score 10,000+ transactions per second on a single CPU.
Q10. How are passwords stored?
Hashed with scrypt via Werkzeug, with per-user salt. The plaintext password is never stored anywhere.
Q11. How does face login work?
face-api.js (a JavaScript port of FaceNet) extracts a 128-dim numeric embedding from a webcam frame. We store this on the user record. At login, we capture a fresh embedding and compute cosine similarity; if ≥ 0.6, the match passes.
Q12. How do you prevent SQL injection?
All queries go through SQLAlchemy ORM, which uses parameterised statements. We never concatenate user input into SQL strings.
Q13. Why is the rule engine weighted only 35%?
The ML model has seen far more data than any individual rule encodes, so it is the primary signal (65%). Rules are a stable safety net and provide explanations; they are not the sole decider.
Q14. How do you avoid false positives that annoy real customers?
By tuning the thresholds: only scores ≥ 0.85 lead to a decline; scores 0.65-0.85 only trigger a review (analyst can approve in seconds). The recall vs. false-positive trade-off is monitored continuously.
Q15. How do you retrain the model on new data?
Run python main.py --mode train --data <new_csv>. The new fraud_model.pkl is saved and picked up on next app restart. In production this is scheduled weekly via cron.
Q16. What if the model file is missing or corrupt?
main.py checks for it at startup, and if it cannot be loaded, automatically retrains from synthetic data so the system never starts in a broken state.
Q17. How is admin access protected?
RBAC via the @admin_required decorator + a global middleware that re-checks role on every request. The audit_log records every admin action.
Q18. How do you handle GDPR / data deletion?
Cascade deletes are configured: removing a user removes their accounts, cards. Audit logs are deliberately kept (denormalised username column) so the trail survives even after deletion — that's a regulatory requirement, not a bug.
Q19. Where would you deploy this in production?
As a Docker container behind nginx on AWS ECS / GKE / Azure Container Apps, with a managed PostgreSQL (RDS), Redis for sessions, S3 for model artefacts, and CloudWatch / Grafana for monitoring.
Q20. What is the biggest limitation today and how would you fix it?
Current ML uses only the current transaction's features — no user history. Adding an LSTM/Transformer that consumes the user's last N transactions (sequence model) would dramatically improve detection of account takeovers.

23. Conclusion

Sentinel is a complete, production-style fraud-detection platform that brings together software engineering, data engineering, and machine learning in a single coherent system. It demonstrates:

  • How a modern Python web stack (Flask + SQLAlchemy) supports a multi-tier application.
  • How a hybrid ML+rules approach satisfies both accuracy and explainability requirements.
  • How role-based access control, audit logging and PCI-DSS-style PAN handling create an enterprise-grade security posture.
  • How real-time UX is achieved with simple HTTP-based streaming.
  • How clean module boundaries (auth / api / admin / banking / models / real_time) keep a 13,000-line codebase maintainable.

The roadmap (deep learning, graph models, federated learning, mobile app) shows clear paths to scale this from a prototype to a multi-tenant, regulator-grade platform.
